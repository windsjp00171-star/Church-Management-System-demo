# 差距報告：現有系統 vs 新規格（Master / PRODUCT / SPEC / 總報告第 17 版）

> 日期：2026-11-06　範圍：Step 1（讀完五份規格）＋ Step 2（盤點現有 repo）。**本文件只盤點，沒有改任何程式。**
> 數字為本 repo 目前 `main` 實測（grep / 靜態掃描）；總報告附錄 H 的數字是舊快照，差異處以本文為準。
> 限制：沒有逐行審完 1.5 萬行；標「待審」的模組動工前仍須逐檔讀過。CodeGraph 尚未可用，以 grep 取代。

## 1. 結論（一頁版）

規格的核心前提是**單一資料底層、稽核只追加、伺服器算、守衛要能被 mutation 弄紅**。現有系統是四個舊專案「複製合併」的單體，**這五個前提目前全部不成立**。

總報告附錄 H 的結論仍然正確：**整包程式不適合直接當底座；適合當「零件庫與文件庫」**。建議做法是「重構成新平台的核心（底層介面＋守衛），再把可用模組一個一個搬進來」，而不是在現有 `routes/` 上就地長出新功能。

### 決定 5 與規格的衝突（依 Rule 7 攤開，採用你的決定）

| 規格原文 | 受影響 | 處理 |
|---|---|---|
| 新表只存 `person_id`（= `users.id`），守衛 20 | 點名表改存「點名名冊成員 id」（點名模組自己的名冊表），不指向 `users` | 守衛 20 對點名模組改為「點名表不得外鍵到 `users`」 |
| 守衛 16「名冊外的人也能被點名」 | 變成常態：所有被點名的人都是點名名冊成員 | 守衛 16 自動成立，可併入 |
| 名冊匯入去重（姓名＋生日＋電話）會連到人的主檔 | 去重只在點名名冊內做 | 規格 5.4 的範圍縮小 |
| 守衛 18「新模組不得直接查 `users`」 | 點名模組反而天然滿足 | 保留 |
| 權限（點名者、查看者、修改者） | 仍需登入者身分，但「被點名的人」與「登入者」是兩件事；點名者／查看者的授權仍用現有登入帳號 | 只有「操作者」引用 `users.id`（寫稽核用），被點名者不引用 |
| 日後要把出席接到會友資料 | 需另做「點名名冊成員 ↔ 人」的對應，不在第一階段 | 預留一個可空的對應欄位？**待你決定**（建議不預留，真要接時再加；符合 Rule 2） |

連帶影響：
- 出席率引擎的分母、離開／中途加入者，都以「點名名冊成員」為單位，不受帳號合併或封鎖影響。
- 個人出席仍屬高敏感資料：名冊成員只存姓名（必要）與選填欄位，不存身分證；稽核只追加；匯出留記錄。
- 帳號合併（守衛 21、22）與點名完全無關，重構順序中階段 C 可獨立進行，不會被點名卡住。
